# 操作と通信のアーキテクチャ

## 目的

CLI、Web UI、MCPで、同じ操作の意味と失敗時の扱いを共有します。
機能を追加するときは共通Commandsを拡張し、必要な入口へ公開します。
仕様の正本はGitHub Issueです。RPC移行の合意と受け入れ条件は[Issue #75](https://github.com/yuske-nakajima/zatto/issues/75)に記載しています。
個別メソッドの引数と戻り値は、アプリに同梱する英語版と日本語版のAPIドキュメントを参照してください。

## 通信経路

```text
Web UI ────────────────────┐
CLI ──────────────────────┼─ HTTP JSON-RPC 2.0 ─ RPC受付 ─ Commands ─ Store
MCPクライアント ─ stdio MCP ─ MCPアダプター ─┘                  │
                                                           └─ 更新の配信処理 ─ WebSocket ─ Web UI

ブラウザー ─ HTTP ─ HTML、相対アセット、静的ファイル、組み込みDocs
```

操作の内部通信はHTTP上のJSON-RPC 2.0へ統一します。
REST操作ルートを残す互換構成は採用しません。
ファイル配信と更新通知は操作の要求・応答とは異なる役割を持つため、それぞれHTTPとWebSocketを使います。
MCPは外部クライアント向けのstdio接続を維持し、サーバー内の状態取得には共有RPCクライアントを使います。

## 責務

| 層 | 担当すること | 担当しないこと |
|---|---|---|
| 共有契約 | 操作名、引数、結果、共通エラーの型 | HTTP、UI、ファイルへの書込み |
| RPCクライアント | 要求ID、JSON送受信、応答の照合、通信エラー、キャンセル | 業務操作の再実装 |
| RPC受付 | メッセージ形式、標準エラー、notification、batch、Commandsへの委譲 | ファイル登録やワークスペース更新の実装 |
| Commands | 入力検証、識別子の照合、操作の実行、業務エラー、保存後の通知 | HTTPレスポンスの直接生成 |
| Store | 永続データの読取り、直列化した変更、原子的な保存 | HTTP、ブラウザー表示、RPCメッセージ |
| UI・CLI・MCP | 入力の収集、操作の選択、結果の表示 | Storeへの別の書込み経路 |

ビュー配信やファイル監視は、登録状態を読み取る専用の経路を持ちます。
業務操作の追加を理由に、これらの読取り経路へ状態変更を混ぜません。

## 一貫性とエラー

ワークスペース識別子は、操作を開始した画面の選択が有効であることを確認する条件です。
任意の別ワークスペースへ書き込む権限を表しません。
照合後は対象を捕捉し、ネイティブダイアログの待機中に選択が変わっても、開始元を対象とします。
保存に失敗した操作は、メモリーと保存済みファイルを変更しません。

メッセージ形式の誤りにはJSON-RPCの標準エラーを使います。
業務上の失敗には共有エラーコードと種類を使い、呼び出し元が文言の比較で判断しない構成にします。
予期しない内部エラーの詳細はサーバーへ記録し、スタックトレースをクライアントへ返しません。
操作が完了した後に必要な更新を配信し、未保存の状態を通知しません。

## notificationとbatch

結果を必要とする操作にはID付きrequestを使います。
notificationは成功・失敗とも応答を返さず、失敗をサーバーログへ記録します。
batchは入力順に逐次実行し、各操作を独立して扱います。
途中の失敗でも残りの操作を続け、batch全体のロールバックは行いません。
後続の操作は、先行する操作が変更した状態を参照します。
停止操作は、受け付けた単体要求またはbatchの応答を完了してからサーバーを停止します。

## 接続と更新

CLIはruntime recordとlockから接続先を判断し、サーバーの識別子と通信バージョンを照合します。
稼働中の旧サーバーを検出した場合、登録、新サーバーの起動、runtimeの削除、自動killを行いません。
旧health APIへの読取りは、旧サーバーの診断に限定します。

REST操作APIの廃止は公開契約の非互換変更のため、2.0.0で導入します。
更新前は旧版の`zatto --stop`で停止します。
更新済みの場合は`npx --yes @yuske-nakajima/zatto@1.2.0 --stop`で旧サーバーを停止し、新版の`zatto`を起動します。
独自ポートでruntime recordがない場合、旧版の停止コマンドへ`--port <検出したポート>`を付けます。
ワークスペースの永続形式version 2と交換形式version 1は維持します。
ファイル識別子、星、並び順を引き継ぎ、通信方式の変更だけを理由にデータを初期化しません。

## 機能を追加する手順

1. 関連Issueの本文とコメントを読み、操作の目的と受け入れ条件を確認する。
2. 共有契約へ操作の引数、結果、必要なエラーを定義する。
3. Commandsへ検証と処理を追加し、Storeの保存と通知の順序を保つ。
4. 必要なUI、CLI、MCPから共有RPCクライアントを使って呼び出す。
5. 不正入力、識別子の不一致、保存失敗、並行操作、結果の表示を検証する。
6. 個別仕様は同梱の英日Docs、横断的な判断はこの文書と概要へ反映する。
7. 配布物を検証し、リリース対象ならバージョニング方針に従って更新する。

操作層の責務、通信方式、永続化の方式を変える場合は、実装前にユーザーとの壁打ちで合意します。
既存の責務内で操作を追加する実装判断は、この手順に従って進めます。

## 配布版と変更履歴

ロゴ直下の版はpackage.jsonを正本とし、ビルド時にブラウザーへ渡します。
サーバーの通信バージョンとは別の識別子です。

公開済みの履歴はGitHub Releasesから取得し、原文と描画用HTMLを原本へ保存します。
同梱ページは許可したHTML要素とHTTPSリンクから再生成し、外部リソースを読み込みません。
履歴は英語・日本語のDocsから開けます。公開済み本文の言語は変えません。
未公開の変更は公開履歴から分け、公開済みの版として表示しません。

再取得は`node scripts/update-changelog.mjs --refresh`で実行します。
原本と英日ページを同じコミットへ含めます。
`node scripts/update-changelog.mjs`はネットワークを使わず再生成します。
通常のビルドやインストール時にはGitHubへの接続を必要としません。
